## AWS IAM Roles Anywhere

These resource control policy (RCP) examples provide guidance for protecting AWS Identity and Access Management Roles Anywhere configuration and restricting session creation to approved trust anchors and expected networks.

**Note:** RCPs do not grant permissions. They define the maximum permissions available to resources in member accounts. A principal must still receive permission from an applicable identity-based or resource-based policy, and an explicit deny in any applicable policy overrides an allow.

| Included policy | Rationale |
|---|---|
| [Deny certificate revocation list state changes except for a specific role](IAM-RolesAnywhere-Deny-crl-state-change-if-not-specifc-role.json) | Deny `rolesanywhere:DisableCrl` and `rolesanywhere:EnableCrl` on all resources unless `aws:PrincipalArn` matches the configured privileged role. Replace `${Account}` and `[PRIVILEGED_ROLE]` before deployment. |
| [Protect critical profiles from changes except by a specific role](IAM-RolesAnywhere-Deny-profile-state-change-if-not-specifc-role.json) | Deny `rolesanywhere:DisableProfile`, `rolesanywhere:EnableProfile`, `rolesanywhere:UpdateProfile`, and `rolesanywhere:DeleteProfile` when the profile has `SecurityTier=Critical` and `aws:PrincipalArn` does not match the configured privileged role. Untagged profiles and profiles with another value are unaffected. Replace `${Account}` and `[PRIVILEGED_ROLE]`. |
| [Protect critical trust anchors from changes except by a specific role](IAM-RolesAnywhere-Deny-trust-anchor-state-change-if-not-specifc-role.json) | Deny `rolesanywhere:DisableTrustAnchor`, `rolesanywhere:EnableTrustAnchor`, `rolesanywhere:UpdateTrustAnchor`, and `rolesanywhere:DeleteTrustAnchor` when the trust anchor has `SecurityTier=Critical` and `aws:PrincipalArn` does not match the configured privileged role. Untagged trust anchors and trust anchors with another value are unaffected. Replace `${Account}` and `[PRIVILEGED_ROLE]`. |
| [Deny session creation from unexpected public CIDR networks](IAM-RolesAnywhere-Deny-startsession-from-unexpected-networks-cidr.json) | Deny `rolesanywhere:CreateSession` on all resources when `aws:SourceIp` is outside the configured trusted CIDRs or the key is absent. Replace the documentation-only `203.0.113.0/24` range with all required trusted IPv4 and IPv6 ranges. |
| [Deny session creation outside approved VPC source-IP CIDRs](IAM-RolesAnywhere-Deny-start-session-from-unexpected-vpc-source-ip-cidrs.json) | Deny `rolesanywhere:CreateSession` on all resources when `aws:VpcSourceIp` is outside the configured private IPv4 and IPv6 CIDRs or the key is absent. Replace `10.0.0.0/16` and `2001:db8:1234:5678::/64` with trusted ranges. Because private addresses can overlap, pair this control with an approved VPC endpoint when CIDRs do not uniquely identify the network. |
| [Deny session creation outside approved VPC endpoints](IAM-RolesAnywhere-Deny-startsession-from-unexpected-networks-vpce.json) | Deny `rolesanywhere:CreateSession` on all resources when `aws:SourceVpce` differs from the configured endpoint IDs or the key is absent. This also denies public-endpoint requests. Replace `vpce-0123456789abcdef0` and include every approved endpoint. |
| [Deny session creation outside VPC endpoints owned by an approved organization](IAM-RolesAnywhere-Deny-start-session-from-unexpected-networks-vpce-orgid.json) | Deny `rolesanywhere:CreateSession` on all resources when `aws:VpceOrgID` differs from `${OrganizationId}` or the key is absent. **Important:** AWS currently documents this key for select services and does not list IAM Roles Anywhere as supported. Do not deploy this example until support is confirmed because an unavailable key can cause every session request to be denied. |
| [Deny session creation outside approved VPC endpoint organization paths](IAM-RolesAnywhere-Deny-start-session-from-unexpected-networks-vpce-orgpaths.json) | Deny `rolesanywhere:CreateSession` on all resources when every value in `aws:VpceOrgPaths` is outside `${OrganizationId}/${RootId}/${OrganizationalUnitId}/*`, or when the key is absent. **Important:** AWS currently does not list IAM Roles Anywhere as supporting this key. Treat this example as illustrative until support is documented and tested. |
| [Deny session creation for unapproved trust anchors](IAM-RolesAnywhere-Deny-start-session-for-unexpected-trust-anchor.json) | Deny `rolesanywhere:CreateSession` for resources other than the trust anchor identified by `arn:aws:rolesanywhere:${Region}:${Account}:trust-anchor/${Privileged-Trust-Anchor-Id}`. Because the policy uses `NotResource`, the named trust anchor is excluded from this deny but is not granted access. Replace every ARN placeholder before deployment. |

### Customization and deployment considerations

- Replace every template or sample value before deployment, including `${Account}`, `${Region}`, `${OrganizationId}`, `${RootId}`, `${OrganizationalUnitId}`, `${Privileged-Trust-Anchor-Id}`, `[PRIVILEGED_ROLE]`, example CIDRs, and `vpce-0123456789abcdef0`.
- Update the `arn:aws` partition where required, and include the complete IAM path when configuring a privileged role ARN.
- The privileged-role and approved-trust-anchor exceptions only avoid their respective explicit denies; they do not grant permission.
- The profile and trust-anchor state-change policies apply only to resources whose existing `aws:ResourceTag/SecurityTier` value is exactly `Critical`. Protect who can assign or remove this classification tag.
- `aws:VpcSourceIp` is populated for requests through a VPC endpoint and represents the request's private source IP. It differs from `aws:SourceIp`; pair it with `aws:SourceVpce` when overlapping private ranges could otherwise match.
- Negated `IfExists` conditions and `ForAllValues:StringNotLikeIfExists` in these deny statements also match when their condition key is absent. The network controls therefore deny requests made through paths that do not supply the required key.
- `aws:VpceOrgPaths` is multivalued, so its policy uses a set operator. The trailing `/*` in the configured OU path includes accounts in that OU and its descendant OUs.
- AWS supports `aws:VpceOrgID` and `aws:VpceOrgPaths` only for documented subsets of services, which currently do not include IAM Roles Anywhere. Do not deploy either endpoint-organization example until support is documented and tested.
- Treat the CIDR, VPC source-IP, endpoint-ID, endpoint-organization, and endpoint-organization-path policies as alternative network-perimeter patterns unless workloads are expected to satisfy every applicable policy. Multiple explicit denies are cumulative.
- Test these policies in a dedicated account or organizational unit before progressively deploying them to production workloads.
